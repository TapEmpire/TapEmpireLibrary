# TEL 3.01.00 — migration guide

Level execution, the message bus, level save data, the game/settings services and every core system
(input, UI, raycast, camera) moved from the game project into TEL. Every section below lists what
changed in **TEL** and what had to change in the **project** (done in PopDrop, to be repeated in
WordGame).

Serialized changes are called out separately — they do **not** produce compile errors and will
silently null out if missed.

---

## 1. Level execution moved to TEL

**TEL** — new `Runtime/CoreSystems/LevelExecutionCoreSystem/`:

| File | Notes |
|---|---|
| `Data/LevelExecutionData.cs` | typed on `TapEmpire.Level.LevelSettings`; `OnResourceSpent`/`ResourceSpent` removed (unused) |
| `Data/LevelStateData.cs` | `AddStepDone` now sets `LevelState.Won` when `StepsDone >= StepsTotal`; `Initialize` raises `OnDataChanged` like the other two mutators; `IsOver` and `SetStepsTotal` removed |
| `Data/LevelState.cs`, `Data/LevelEndReason.cs`, `Data/FlowAction.cs` | enums, previously inside the interface file |
| `ExecutionActions/{Ads,Iap,Network,RateMe}ExecutionAction.cs` | unchanged behaviour |
| `ILevelExecutionCoreSystem.cs` + `LevelExecutionCoreSystemExtensions.cs` | see API changes below |
| `LevelExecutionCoreSystem.cs` | new base class |
| `Progress/ProgressExtensions.LevelExecution.cs` | see section 4 |

`ILevelExecutionCoreSystem` API changes:

- Signals are **R3-only**. `OnLevelStarted` / `OnLevelCompleted` are now `Subject<T>`; the
  `event Action<>` duplicates are gone, and `OnCycleCompleted` became `Subject<int>`.
- `RestartLevel(bool isDebug)` → `RestartLevel()` (the parameter was never read).
- `TryGetCamera` extension removed.
- `Levels` is typed `IReadOnlyList<TapEmpire.Level.LevelSettings>`.

The new `LevelExecutionCoreSystem` base owns: `ExecutionData`, `ExecutionModules`,
`_defaultLevelView`, `_diContainer`, `_coreSceneReferences`, `_disposables`, `_executionAction`,
`OnRelease`, `virtual DestroyLevel()`, `InitializeLevelView()`, `InstantiateLevelView()`,
`InitializeModules()` and `virtual OnLevelStateChanged()`.

**Project**:

- Delete the moved files; the game class derives from the TEL one:
  `class LevelExecutionCoreSystem : TapEmpire.CoreSystems.LevelExecutionCoreSystem, ILevelExecutionCoreSystem`.
- Rename the game class's `[Inject] Construct` → `ConstructDerived` and drop the `DiContainer` and
  `ICoreSceneReferences` parameters (the base injects them). Zenject injects both methods, base first —
  they must not share a name.
- Delete the game copies of `DestroyLevel`, `InitializeLevelView`, `InstantiateLevelView`,
  `InitializeModules`, and the no-op `OnInitializeAsync` override.
- Keep game-only bits as overrides: `DestroyLevel()` calling `base` then closing the level-end popup,
  and `OnLevelStateChanged()` for the win/lose flow.
- Migrate event subscribers to R3: `x.OnLevelCompleted += H` → `x.OnLevelCompleted.Subscribe(H).AddTo(_disposables)`.
  In PopDrop this was `AnalyticsCoreModule` and `CustomCursorUIView`.

## 4. Level save data moved to TEL

**TEL** — `Runtime/CoreSystems/LevelExecutionCoreSystem/Progress/ProgressExtensions.LevelExecution.cs`
holds a `LevelSaveData` base (just `LevelName`) and generic extensions:

```csharp
T    GetLevelSaveData<T>()  where T : LevelSaveData, new()
void SetLevelSaveData<T>(T) where T : LevelSaveData
void CleanLevelSaveData()
bool HasLevelSaveData()
string GetLevelSaveName()
```

Storage stays `StringValuesDictionary` via `Get/SetSerializableObject`, so it remains part of the
cloud-save snapshot. `HasLevelSaveData` reads the raw string; `GetLevelSaveName` deserializes into
the **base** type, so TEL answers both without knowing the game's payload.

**Project** — delete the game's level-save extensions. Games with a payload define
`class XLevelSaveData : LevelSaveData` and use the generic pair. `Has`/`Clean` call sites are
unchanged. Anything the old `CleanLevelSaveData` also wiped (hint/lens state in WordGame) must move
to the game's call site.

### Unity value types in serializable progress payloads

Follow-up, made while giving PopDrop's level save an orb list.

**TEL** — new `Runtime/Utility/Json/UnityJsonSettings.cs` holds a single cached
`JsonSerializerSettings` bundling the three converters that already sat in that folder
(`Vector2Converter`, `Vector3Converter`, `QuaternionConverter`), and
`ProgressServiceExtensions.Get/SetSerializableObject` now pass it. Everything layered on those two
helpers inherits it — `Get/SetLevelSaveData<T>`, the LiveOps pair, `Offer`, IAP's `SpendData` — with
no signature changes.

This is a **fix, not an optimisation**. Serializing a Unity `Vector2` through plain Newtonsoft does
not merely produce verbose JSON: `normalized` is a public get-only property returning a `Vector2`,
get-only properties are written by default, and a normalized vector's `normalized` is itself
(`Vector2.zero.normalized` is `zero`), so there is no terminating case and no reference-loop
detection to catch it — it recurses until the stack dies.

That is also why making it the default is safe rather than a data migration: the only payloads whose
reading changes are ones containing these types, and those could never have been written. The
settings are cached because the level save is written on every merge; the converters cost three
reference comparisons per serialized value, which is nothing against the `PlayerPrefs.Save()` that
follows every write.

Precision is deliberately **not** part of this. Rounding is a property of the data, not the
serializer, so a game that wants short floats rounds when it builds the payload — a 3-decimal value
round-trips exactly through Newtonsoft's shortest-round-trip float formatting.

### The base owns loading the save

**TEL** — `LevelExecutionCoreSystem` is now generic:

```csharp
public class LevelExecutionCoreSystem<TLevelSaveData> : ExecutionCoreSystem, ILevelExecutionCoreSystem
    where TLevelSaveData : LevelSaveData, new()
{
    public TLevelSaveData LevelSaveData { get; private set; }

    protected virtual TLevelSaveData LoadLevelSaveData(LevelSettings levelSettings);
    protected virtual TLevelSaveData CreateLevelSaveData(LevelSettings levelSettings);
}
```

`StartLevel` calls `LoadLevelSaveData` **before** `InitializeLevelView`, which is the whole point:
the save must be resolved before `ExecutionData.Value` is published, or every core system reading it
in its `ExecutionData` handler races the load. Games should not have to rediscover that ordering —
before this, PopDrop overrode `StartLevel` purely to buy it.

`LoadLevelSaveData` reads, compares `LevelName` against `levelSettings.FullName`, **cleans** a
mismatched save and falls back to `CreateLevelSaveData`. Cleaning rather than ignoring matters:
`HasLevelSaveData` reads the raw string, so a stale save left in place keeps the menu offering
"Continue" for a level that will never load. The base default of `CreateLevelSaveData` returns
`new TLevelSaveData { LevelName = levelSettings.FullName }`; games override it to seed their payload.

The type parameter — rather than a base-typed property plus `new` shadowing, as with
`GameSettings`/`LevelsTable` — exists for two reasons. It avoids two same-named members where
picking the wrong one compiles and silently loses the payload, on a property every core system reads
each level start. And it supplies the concrete type for deserialization, so the base can call
`GetLevelSaveData<TLevelSaveData>()` itself instead of needing a second virtual for the typed read.

TEL owns load, validate and clean; it does **not** own writing. Save cadence is irreducibly
game-specific (PopDrop writes on merge, on drop, on field shift, and on a debounced settle timer),
so `LevelSaveData` has a `private set` and games mutate the instance and call `SetLevelSaveData`
on their own rules.

`ILevelExecutionCoreSystem` cannot declare the property (it does not know the parameter), so it
stays off the TEL interface and each game's interface declares it with the concrete type — which is
what you want, since only the game's type has a payload.

**Project** — this supersedes the guidance above about defining `XLevelSaveData` and calling the
generic pair by hand:

- Derive from the closed generic: `class PopDropLevelExecutionCoreSystem : LevelExecutionCoreSystem<LevelSaveData>`.
  A game with no payload writes `LevelExecutionCoreSystem<LevelSaveData>` using TEL's own type; if
  the bare name is wanted back, a two-line `LevelExecutionCoreSystem : LevelExecutionCoreSystem<LevelSaveData>`
  restores it.
- Delete any game-side load, validation or `StartLevel` override that existed to run it, and keep
  only a `CreateLevelSaveData` override for payload defaults.
- Declare `LevelSaveData LevelSaveData { get; }` on the game's interface. An inherited property
  satisfies it — no `new`, no cast.
- Name collision to expect: a game payload named `LevelSaveData` is ambiguous against
  `TapEmpire.Services.LevelSaveData` in any file importing both `TapEmpire.Services` and the game's
  data namespace. The usual dodge for `LevelSettings` (not importing the colliding TEL namespace)
  is unavailable, since `TapEmpire.Services` carries `IProgressService` and the UI services. PopDrop
  uses a using alias: `using LevelSaveData = PopDrop.Level.LevelSaveData;`.

### Two disposable lifetimes

**TEL** — `LevelExecutionCoreSystem` now carries both:

| Field | Lifetime | Created | Disposed |
|---|---|---|---|
| `_disposables` | the system | field initializer | `OnRelease` |
| `_levelDisposables` | one level | `StartLevel` | `DestroyLevel` |

This is what the sibling core systems already do (`MergeCoreSystem`, `LevelOutcomeCoreSystem`), and
it fixes a trap rather than just renaming. `_disposables` was declared as a plain field, initialized
once at construction, then **reassigned inside `StartLevel`** — so it looked like a system-lifetime
bag and was actually per-level. A derived class doing the obvious thing (subscribe in
`OnInitializeAsync`, `.AddTo(_disposables)`) had its subscription silently thrown away at the first
level start, with no error anywhere.

`OnRelease` tears down level scope before system scope (`DestroyLevel()` then
`_disposables.Dispose()`) because `DestroyLevel` publishes `ExecutionData.Value = null`, and
system-lifetime subscribers should observe that teardown before their subscriptions are dropped.

**Serialized** — nothing. **Silent** — yes: any subclass line `.AddTo(_disposables)` still compiles
and changes meaning, from "dies each level" to "lives for the system". Audit those call sites when
migrating a game (PopDrop had none).

### A completed save wins the level at start

**TEL** — the win rule moved into the data that owns it. `LevelStateData` gained a private
`CheckWin()` (`StepsDone >= StepsTotal` → `LevelState.Won`) called by **both** `Initialize` and
`AddStepDone`, so restoring `StepsDone` from a save reaches the same conclusion as playing the last
merge. Note there is no `StepsDone > 0` guard, matching `AddStepDone` exactly — a level authored with
`StepsTotal == 0` is therefore won the moment it starts.

`StartLevel` ends with an unconditional catch-up call:

```csharp
OnLevelStateChanged(ExecutionData.Value.LevelStateData);
```

Same subscribe-then-call-directly idiom as the `ApplyPause()` / `ApplyTicksPause()` pair in
`InitializeLevelView`, and needed for the same reason: `Initialize` runs *inside* the
`ExecutionData.Value` assignment, one line before TEL subscribes to `OnDataChanged`, so a
won-on-load state would otherwise fire into no subscribers — leaving the level in `Won` with no
popup, no level advance and no save clean, and nothing later to rescue it (`AddStepDone` only fires
on a move, and a board at its target may have none left).

It must be the **last** statement in `StartLevel`. The win path calls
`SetLevelProgress(index + 1)`, and `StartLevel` calls `SetLevelProgress(index)` just after
`OnLevelStarted` — fire the check any earlier and the level advance is silently overwritten, so the
player replays the level they just finished. That also rules out the tidier-looking fix of
subscribing before publishing `ExecutionData.Value`.

The call is unconditional because every `OnLevelStateChanged` override already switches on the
state, so `Active` is a no-op. **Silent** — an override that assumes it is only invoked on a
*transition* will now also see one call per level start.

**Project** — a game whose outcome system initializes `LevelStateData` must subscribe **before**
calling `Initialize`, or it misses the notification for a save that is already complete. In PopDrop
`LevelOutcomeCoreSystem` moved its `Initialize` call below its three subscriptions; without that,
its `.Where(Won or Lost) → dispose` never fires on a won-on-load level, `_dropBoxCoreSystem.State`
stays subscribed, and `OnUpdateDropBoxState` — which has no guard on the current state — flips an
already-won level to `Lost` on the next `LateTick`.

## 5. Settings reorganised

### SystemSettings gains the build/device flags

**TEL** — `Debug`, `FrameRate` and `IgnoreConnection` moved from `GameStartSettings` to
`SystemSettings`; `ISystemService.StaticSettings` is **deleted** (it was `GameStartSettings`).
`IgnoreConnection` now sits with `PlayOfflineForPayers`/`PlayOfflineNoAds`, so `CanPlayOffline`
reads one asset.

**Project** — repoint every `Debug` reader to `ISystemService.SystemSettings.Debug`. In PopDrop:
`UICoreSystem` and `MenuSceneStarter` switched from `IGameGenericService` to `ISystemService`;
TEL-side `OfferUIView` and `LunarConsoleStartAction` were updated in the library.

Delete any hardcoded `Application.targetFrameRate = 60` in scene starters — `EntrySceneStarter`
applies `SystemSettings.FrameRate` and it persists across scene loads. `EntrySceneStarter` holds the
asset by `[SerializeField]` (it runs before services), so its field became `SystemSettings`.

### GameStartSettings → GameSettings

**TEL** — renamed, reduced to plain public fields, and now:

```csharp
public enum WinFlow { Next, Menu }

public bool AutoRestartLevel;

[Header("Ads")]
public bool AdsOnQuit = false;
public bool AdsOnRestart = true;

[Header("Win flow")]
public WinFlow WinFlow = WinFlow.Next;
public List<int> WinFlowExceptionLevels = new();
```

Removed: the field/property sugar, `OnDataChanged`/`BroadcastUpdate`, `HideRewardsAds`,
`EditorDebugStartLevelIndex`, `EditorStartFromPrefLevel` (all unused — the last two fed
`CoreSceneStarter.GetStartLevelIndex()`, itself dead), and `SkipInters` (see below).

`WinFlow` replaces `SkipMenuRedirectOnLevelComplete`. The enum is the default destination after a
win; the list is the levels where the opposite applies, in **designer numbering** (`index + 1`) for
the **completed** level. The old list held the *next* level's raw index, so entries shift.
Empty list = pure strategy.

`NoAdsOnQuit` became `AdsOnQuit` (inverted) plus `AdsOnRestart`; `Next` always allows ads.

**Project** — apply in the level execution system:

```csharp
private bool AreAdsAllowed(FlowAction flow) => flow switch
{
    FlowAction.Quit => _gameSettings.AdsOnQuit,
    FlowAction.Restart => _gameSettings.AdsOnRestart,
    _ => true,
};

private FlowAction ConvertNextAction()
{
    var completedLevel = ExecutionData.Value.LevelIndex + 1;
    var winFlow = _gameSettings.WinFlow;
    if (_gameSettings.WinFlowExceptionLevels.Contains(completedLevel))
        winFlow = winFlow == WinFlow.Next ? WinFlow.Menu : WinFlow.Next;
    return winFlow == WinFlow.Next ? FlowAction.Next : FlowAction.Quit;
}
```

To keep the old WordGame behaviour ("menu after every win except the first level"):
`WinFlow = Menu`, `WinFlowExceptionLevels = [1]`.

### SkipAds moved to AdsConfig

**TEL** — `AdsConfig` gained `SkipAds` (next to `TestMode`); `AdsService.SkipAds` now reads/writes
`_settings.Config.SkipAds` instead of being a runtime-only property. It stays out of `AdsSettings`
because that is the remote-tunable surface.

**Project** — delete `GameStartSettings.SkipInters` and the bridge that pushed it into
`IAdsService.SkipAds` (in PopDrop this was the only reason `GameGenericService` injected
`IAdsService`). Debug UIs set `IAdsService.SkipAds` directly.

## 7. Input core system moved to TEL

**TEL** — new `Runtime/CoreSystems/InputCoreSystem/` (`IInputCoreSystem.cs`, `InputCoreSystem.cs`,
`InputMode.cs`), merged from the three copies that had drifted apart in WordGame, PopDrop and
StickerGame:

| Change | Came from |
|---|---|
| Signals are **R3-only** — `Observable<Vector2> OnScreenInputStart` / `OnScreenInputEnd`; the `event Action<Vector2>` duplicates are gone | StickerGame, minus its `R3` name suffix |
| `Observable<Vector2> OnScreenTapEnd` — fires when a touch ends within `0.2s` and `10px` of its start, emitting the **start** position | StickerGame |
| `TouchPhase.Stationary` counts as hold alongside `Moved` | PopDrop |
| `StartInput(Vector2 position, bool withPress = true)` | WordGame |
| `EndInput` does **not** reset `SimulatedPosition` | WordGame / PopDrop |
| `InputMode` is a `[Flags]` enum on a serialized field | new |

`InputMode` became `[Flags] { None = 0, Drag = 1, Tap = 2, Drawing = 4 }` — design-time gesture
config, editable on the installer entry in the scene (mask dropdown). It replaces the runtime
`InputModeProperty` (a `ReactiveProperty` no project ever read): the interface now exposes get-only
`InputMode InputMode`, backed by `[SerializeField] private InputMode _inputMode`, defaulting in
code to `Drag`. Tap detection emits `OnScreenTapEnd` only while the `Tap` flag is set — `Tick`
gates the `CheckTouch` call in the `Ended`/`Canceled` case, so toggling the flag in the Inspector
takes effect on the next touch (`SaveTouch` on `Began` stays unconditional so the start data is
fresh if the flag turns on mid-touch). `None` means "no gestures recognized" — test it with `==`,
never `HasFlag` (`x.HasFlag(None)` is always true).

Why `Stationary` matters: it previously fell into the `default` branch and reset every flag, so a
motionless finger reported `IsInputHold == false` on device while the mouse fallback — which maps a
held button to `Moved` every frame — reported `true`. Editor and device now agree.

`withPress: false` places the simulated cursor without firing a press; the autoplay/creatives flow
uses it to glide the on-screen finger to a target before pressing, then chains the next gesture from
`InputPosition` — which is why `EndInput` must not zero `SimulatedPosition`.

Tap detection is currently unconditional. If a game needs it off, gate it before shipping.

### UI gate

`[SerializeField] private bool _blockInputOverUI = true` makes the input system itself drop gestures
that begin over UI, so a tap on a HUD or debug button no longer reaches gameplay. Previously every
consumer polled raw `Input`, which knows nothing about the `EventSystem`, and the button and the
gameplay handler both fired.

The check runs **once per gesture**, on the `Began` frame, and latches into `_uiOwnsInput`: while
set, all three subjects stay silent and the `IsInput*` flags stay false for the rest of that touch,
clearing on `Ended`/`Canceled` or when the touch disappears. Latching is what covers press-on-button
→ drag-onto-field → release, which a per-frame check would let through at the release. `IsSimulated`
input is never gated — tutorial and autoplay gestures must still reach gameplay through UI.

`IsInputOwnedByUI` sits above the phase `switch`, not inside it, and `Tick` reads as one early
return. The latch spans phases by definition, so folding it into the `switch` would repeat the guard
in the `Began`, `Moved`/`Stationary` and `Ended`/`Canceled` cases — and a case added later that
forgets it leaks input on part of a gesture. Keeping it hoisted means the `switch` stays purely
about phase semantics and "a UI-owned gesture emits nothing" is one readable statement. Note it
returns `true` for the `Ended` that clears the latch, so that final phase is swallowed too.

`IsPointerOverUI` does an explicit `EventSystem.RaycastAll` at the press position, into a
`PointerEventData` and a `List<RaycastResult>` held as fields (allocated in `OnInitializeAsync`,
reused per call). Deliberately **not** `EventSystem.IsPointerOverGameObject(fingerId)`, which the
studio's other copies use: that returns the pointer state cached by the last input-module pass, and
`EventSystem` is a plain MonoBehaviour whose Update order against the Zenject `SceneContext` tick is
unpinned — so on the `Began` frame, the one frame we care about, it can still report the pre-touch
state and let the tap through. It also needs `#if`s to pick the pointer id (touch `fingerId` vs
mouse `-1`), as in CoinSort's `RayInputCoreSystem`. The raycast is order-independent, single-path,
and costs one extra graphic raycast per tap.

This replaced `Runtime/Utility/MiscUtilities/RaycastUtility.cs`, **deleted** — it had no callers in
any project (every game carried its own `RaycastUtils` copy), its editor branch was gated on
`Input.GetMouseButtonDown(0)` so it only answered truthfully on the press frame, and its device
branch allocated a `PointerEventData` and a `List` per call.

**Project**:

- Delete the game's `IInputCoreSystem`, `InputCoreSystem` and `InputMode`. Consumers that already
  `using TapEmpire.CoreSystems` need no edit once the game-side duplicates are gone — in PopDrop
  that covered `UICoreSystem` and `RaycastUICoreSystem`.
- Migrate event subscribers to R3: `x.OnScreenInputStart += H` →
  `x.OnScreenInputStart.Subscribe(H).AddTo(_compositeDisposable)`. In PopDrop this was
  `CustomCursorUIView`, whose `OnDestroy` override existed only to unsubscribe and was deleted —
  `BaseCustomCursorUIView.OnDestroy` already disposes the composite.
- WordGame's `CoreSystems/Input/` also holds a `PlatformUtility` duplicating
  `TapEmpire.Utility.PlatformUtility`; delete it with the folder.
- StickerGame's copy is already in the `TapEmpire.CoreSystems` namespace, so deleting its
  `CoreSystems/Input/` folder is the whole migration there, plus the `DragObjects` → `Drag` rename.
- Drop the game's own UI gate once `_blockInputOverUI` is on, or the check runs twice: the
  per-call-site `if (RaycastUtils.IsPointerOverUI()) return;` in RiddleGame (`TapModule2D`,
  `DragModule2D`) and SlimeAway (`TapModule2D`), StickerGame's commented-out line in
  `DragStickerCoreSystem`, and the in-system checks in CoinSort's `RayInputCoreSystem`, ScrewJam and
  DeckRacing. Delete the game-local `RaycastUtils` with the last call site. GooseGame's touch
  adapters bypass `InputCoreSystem` entirely and keep their own per-finger latch.

## 8. Raycast systems moved to TEL

**TEL** — two new folders under `Runtime/CoreSystems/`:

| Folder | Raycasts against | Source |
|---|---|---|
| `RaycastUICoreSystem/` | canvas UI via `GraphicRaycaster`, filtered by tag | the game project, moved as-is |
| `RaycastCoreSystem/` | 2D physics via `Physics2D`, filtered by `LayerMask` | StickerGame (already declared `TapEmpire.CoreSystems`) |

They are separate systems, not two versions of one. StickerGame additionally has
`RaycastUIMetaSystem`, which is the same class as `RaycastUICoreSystem` bound to the Meta scope —
if the Meta half is ever promoted, it should reuse the TEL type rather than fork it again.

`RaycastCoreSystem` changed on the way in: the `Firebase.Crashlytics` logging in `DoRaycast` is
gone (it logged and then returned `default` anyway; a null camera just means no level is running,
so it is now a one-line guard), `CreateDefaultFilter`/`CreateOverlapFilter` merged into one
`CreateFilter(layerMask, useTriggers)` keeping the raycast/overlap trigger asymmetry, `OverlapCollider`
became `Overlap`, and the bare `new Collider2D[10]` became a named constant. It still silently
truncates at 10 hits.

Both systems then stopped being `ITickable`. They used to memoise their per-frame results and null
the cache in `Tick()`, which only worked while the clear reliably ran after every reader — an
invariant that breaks the moment a tick is skipped or reordered, and which silently hands out a
value computed on an earlier frame. The cache now carries a `Time.frameCount` stamp and is dropped
lazily on read, so correctness no longer depends on tick ordering or on the systems ticking at all.
No API changed; a project that resolves them keeps working unmodified.

**Project** — delete the game copies of both. Consumers already importing `TapEmpire.CoreSystems`
need no edit once the duplicates are gone.

### Split layer masks and a non-allocating overlap

Follow-up change, made while wiring PopDrop's merge system:

- `_layers` split into `_raycastLayers` and `_overlapLayers`. One mask cannot serve both: raycasts
  pick input targets (PopDrop: the hex plate) while overlaps query gameplay bodies (PopDrop: orbs),
  and those are different layers. `RaycastHit2DLayered(LayerMask)` stays as the per-call override;
  overlaps get no equivalent until a second caller needs one.
- `Overlap` reuses a buffer instead of allocating `new Collider2D[10]` per call, and no longer
  filters through `IsTouching`. It is now a plain shape query: which colliders intersect this one
  right now.
- The old behaviour survives as `OverlapTouching`, which layers the `IsTouching` filter back on.

The two answer different questions, and the choice is not cosmetic. `IsTouching` reads the contact
list from the last physics step, so it is stale by up to one `FixedUpdate` and reports only pairs
the solver actually registered. StickerGame wants that: its dragged sticker is a kinematic trigger
moved by `transform.position` every frame, so a fresh query on release merges with whatever the
polygon happens to cross that frame — flinging past a neighbour counts as a drop onto it. The stale
check demands the sticker hovered over the target long enough for physics to see it, and pays for it
with the occasional ignored drop released in the same frame the overlap began. PopDrop's merge runs
off real collisions, so it uses `Overlap`.

**Serialized** — `_layers` is not migrated. Existing `RaycastCoreSystem` entries keep their old
`_layers` block, which now deserializes into nothing; re-set both masks in the inspector.

### WordGame loses raycast blocking — read before deleting its copy

WordGame's `RaycastUICoreSystem` carries logic that TEL's does **not**, and it is easy to lose
silently because nothing fails to compile:

```csharp
if (!raycastResults.Exists(x => x.gameObject.GetComponent<IInterceptRaycaster>() != null))
    return raycastResults.Where(result => result.gameObject.CompareTag(tag));
raycastResults.Clear();
return raycastResults;
```

plus `IInterceptRaycaster.cs` — an empty marker interface in the same folder, implemented only by
`CoinTimerView`. The effect: if any hit under the pointer is a marked interceptor, the entire result
set is discarded, so the widget swallows the tap and gameplay beneath it does not react.

PopDrop never had this (it went with the CoinTimer feature during cleanup), which is why the TEL
version does not include it. **Deleting WordGame's copy makes the coin timer click-through.**

Do not port it verbatim — it has a depth bug. `Exists` scans the whole list while
`GraphicRaycaster` returns hits front-most first, so an interceptor *behind* the tagged element
cancels the tap exactly as hard as one in front of it.

The replacement, if the behaviour is still wanted, is a **blocking tag** rather than a marker
component — one mechanism instead of two, and depth-aware:

```csharp
foreach (var result in raycastResults)   // front-most first
{
    if (hasBlockingTag && result.gameObject.CompareTag(_blockingTag)) yield break;
    if (result.gameObject.CompareTag(tag)) yield return result;
}
```

Why a tag beats the marker component:

- `GetComponent` only sees the exact GameObject that was hit. An `Image` with a `Text` child needs
  the marker on every child or a hit on the text slips through; the tag editor applies a tag to a
  whole subtree in one action.
- `CompareTag` is allocation-free; `GetComponent` per hit per frame is not.
- Selecting and blocking stop being two different mechanisms.

Caveats: a GameObject can carry only one tag, and `CompareTag` throws on an undefined tag — so the
empty case must short-circuit, which conveniently keeps blocking opt-in (empty field reproduces
today's TEL behaviour exactly). Decorative or animated UI should use `Graphic.raycastTarget = false`
so it never enters the results at all; the blocking tag is for deliberate blockers only. Opt-in
blocking is the safer default here — a forgotten `raycastTarget` silently eats taps, whereas a
forgotten blocking tag merely lets them through, which is far easier to spot.

## 9. UI core system split into a TEL base

**TEL** — `IUICoreSystem.cs` moved from `CoreSystems/` root into a new
`Runtime/CoreSystems/UICoreSystem/` folder and gained
`ReadOnlyReactiveProperty<bool> IsUIBlocked`. Alongside it, a new abstract `UICoreSystem` base owns
everything generic: the block counter and `BlockUI`, the `IUIService.OnBeforeOpenView` /
`OnAfterCloseView` subscriptions, `ExecutionData` → `BlockUI(data == null)`, the initial
`SceneLoadingUIViewModel` catch-up block, the fan-out into
`IInputCoreSystem.BlockModeProperty`, and the `OnSceneContextInstalled` → `CreateUIAsync` hook.

Composition — which views exist and their view models — stays in the game via
`protected abstract UniTask CreateUIAsync(CancellationToken)`.

**Project**:

- Delete the game's `IUICoreSystem` and `UICoreSystem`. The game class derives:
  `class <Project>UICoreSystem : UICoreSystem`, keeping its `[SerializeField]` view fields.
- `[Inject] Construct` → `ConstructDerived` (same rule as section 1).
- The old `CreateUI` body becomes the `CreateUIAsync` override, and the game's `OnRelease` is
  deleted — the base closes the HUD views it opened.
- The HUD blocker is now pulled, not pushed. `_hudViewModel.IsBlockerEnabled.Value = ...` and the
  `_hudViewModel` field are gone; instead the hud view model subscribes, guarded because
  `CommonHudUIView` also lives in the Menu scene where core systems do not exist:

```csharp
if (diContainer.HasBinding<IUICoreSystem>())
{
    diContainer.Resolve<IUICoreSystem>().IsUIBlocked
        .Subscribe(IsBlockerEnabled.AsObserver())
        .AddTo(_disposables);
}
```

### Open HUD views through `OpenHudViewAsync`, and delete the counter compensation

This is the part that breaks quietly. WordGame's `CreateUI` pre-decrements the block counter once
per HUD view it is about to open:

```csharp
_blockCounter -= 2;                        // CommonHud + CoreHud
...
if (gameStartSettings.Debug) --_blockCounter;   // + CoreDebug
```

Those magic numbers exist because `OnBeforeOpenView` fires for **every** view, so the system counts
its own HUD opens and never sees a matching close (`OnRelease` fires the closes with `.Forget()`
and unsubscribes immediately after). The count equals the number of HUD views, so it differs per
project — WordGame `-2`, PopDrop `-1`.

The base removes the cause instead: `OpenHudViewAsync` records each view model it opens, and
`ShouldBlockFor` excludes anything in that set, so HUD views are never counted in the first place.

**Porting `CreateUI` therefore means two edits, not one** — swap `_uiService.OpenViewAsync(...)` for
`OpenHudViewAsync(...)`, and **delete every `_blockCounter` line**. Keeping them double-compensates
and leaves the counter permanently negative, i.e. the UI never blocks again.

Note an interface-tagging approach does *not* work here: only `CommonHudUIViewModel` implements
`IHudUIViewModel`; `CoreHudUIViewModel` and `CoreDebugUIViewModel` are plain `IUIViewModel`, so a
`viewModel is not IHudUIViewModel` filter would still count two of the three and leave the UI
permanently blocked. Identity tracking is what makes it correct. Historically the original
implementation did filter by type (`popup is not CoreHudUIViewModel and not CoreDebugUIViewModel`);
that filter was lost when the counter arrived, and the base restores its intent.

Also gone: the `if (shouldBlock == _isUIBlocked) return;` guard in the old `BlockInternal`. It dates
from when `BlockUI` was a plain boolean latch with no counter. `_isUIBlocked` is now a
`ReactiveProperty`, which carries an equality comparer and skips notification on an unchanged
value, so the guard is redundant.

### Resource-button blocking stays in the game

WordGame's `IUICoreSystem` also declares `IsResourceButtonsBlocked` and `BlockResourceButtons`, a
second independent counter consumed by `CoreHudUIView` and driven by `LevelIntroCoreSystem`. TEL's
base deliberately does **not** include it — PopDrop dropped it, so there was only one call site to
generalise from. Keep it on the derived game class; because the calls are compile-time references,
this one fails loudly rather than silently.

### Scoped `BlockUI()`

Follow-up, added while blocking gameplay taps during PopDrop's field shift.

**TEL** — `IUICoreSystem` gained a parameterless `IDisposable BlockUI()` alongside
`BlockUI(bool)`. It blocks and returns a token that releases on dispose:

```csharp
public IDisposable BlockUI()
{
    BlockUI(true);
    return Disposable.Create(() => BlockUI(false));
}
```

Purely additive — no `BlockUI(bool)` call site changes. Prefer the scoped form for anything blocking
across an *animation* rather than an `await`: the release rides in a `CompositeDisposable` or a
`UniqueDisposable`, so an abnormal exit (level torn down mid-tween, a `Kill()` that skips
`OnComplete`) cannot leave the counter permanently raised — the failure this guide already warns
about under `_blockCounter`.

When swapping the held token, assign through `UniqueDisposable.Disposable` rather than
disposing and reassigning by hand. The new block is acquired while evaluating the argument, *before*
the setter releases the old one, so the counter goes 1 → 2 → 1 and never dips. The hand-written
release-then-acquire order dips to 0, which synchronously emits `IsUIBlocked = false` and flickers
both the HUD blocker and `InputCoreSystem.BlockModeProperty`.

## 10. Camera core system moved to TEL

**TEL** — new `Runtime/CoreSystems/CameraCoreSystem/`, plus `Runtime/Utility/Bounds/` holding
`IBoundsProvider`, the abstract `BoundsProvider : MonoBehaviour`, and `ExplicitBounds`
(serialized local-space size + centre). `LevelReference.cs` gains `BoundsProviderReference` and
`Vector2Reference`.

The abstract MonoBehaviour base exists for serialization: `LevelReference<T>` stores
`[SerializeField] private T _value` inside a `[SerializeReference]` list, and Unity cannot serialize
an interface-typed field, so the level reference must be typed on a concrete `UnityEngine.Object`.
The interface remains for non-component providers.

`ICameraCoreSystem` is reduced to a single `Adjust()`. `MoveToPoint` and `SetPosition` are gone.

`Adjust()` fits the camera to the level's geometry — width fits exactly, box bottom on the viewport
bottom, with the banner and `_bottomPadding` as a bottom inset:

```csharp
var aspect = (float)Screen.width / Screen.height;
camera.orthographicSize = bounds.size.x * 0.5f / aspect;
camera.transform.position = new Vector3(
    bounds.center.x,
    bounds.min.y - bottomInset + camera.orthographicSize,
    camera.transform.position.z);
```

It reads two level references: `"Geometry"` (a `BoundsProvider`) and `"Canvas"` (only to convert
banner pixels to world units). It re-runs on `ExecutionData` and on `IAdsService.AdsEnabled`.

### What changed versus StickerGame's version

| StickerGame | TEL |
|---|---|
| Moves the **world** — `background.position`, plus a `bottomEdge` UI `anchoredPosition` shift | Moves the **camera** only |
| `camera.orthographicSize *= referenceAspect / currentAspect` | assigns `orthographicSize` outright |
| level references `"Background"`, `"BottomEdge"`, `"Banner"` | one `"Geometry"` bounds reference |
| hardcoded `-175.0f` UI shift when ads are off | `BannerHeight` const, applied while ads are on |
| `ReferenceWidth`/`ReferenceHeight` fields | canvas `scaleFactor`, no reference constants |

Moving content rather than the camera does not survive a physics-driven field: colliders and bodies
would have to be teleported after setup, and authored coordinates stop matching runtime. The
multiply is also non-idempotent — `OnAdsEnabled` re-invokes the same method, so each ad toggle
re-applied the `-175` shift and re-multiplied the zoom. Assigning absolute values makes re-fitting
free and correct.

`BannerHeight` is a `private const`, deliberately not a `[SerializeField]`: a serialized field bakes
a copy into every project's scene, so changing the library default would not propagate. Conversion
uses `canvas.scaleFactor`, which already accounts for the `CanvasScaler` match setting — a
`referenceResolution.y` ratio is only correct when the scaler matches on height.

Dead members dropped on the way in: `_uiService` (injected, never read), `_canvasScaler` and
`_safeZoneMultiplier` (never assigned), `_frame` (only ever set to `null`).

**Project**:

- Put an `ExplicitBounds` on the geometry root and have the geometry setup script write it, so the
  box dimensions keep a single source of truth. In PopDrop, `BorderSetup` gained
  `[RequireComponent(typeof(ExplicitBounds))]` and its `Rebuild()` button ends with
  `SetBounds(new Vector2(w, h), new Vector2(0f, o + h * 0.5f))`.
- Author a `"Geometry"` level reference (`BoundsProviderReference`) pointing at it.
- The bounds should describe the **playable interior**, not the collider envelope — collider
  thickness sits outside the framed area.

## 12. Debug popup framework

**TEL** — new `Runtime/Features/Debug/`, generalised from WordGame's `MenuDebugUIView` page logic
so every debug popup (menu and core scene alike) shares one structure:
popup → pages → components → line widgets.

| File | Notes |
|---|---|
| `DebugUIView.cs` | `DebugUIView<TViewModel> : UIView<TViewModel>, IInjectable` — open/close buttons, content container, `List<DebugPageEntry>` (`{Button, Page}`), page switching, plus the Odin `ToggleVisibility` / `OpenPage` editor buttons |

Design notes:

- Pages and components never receive the popup's view model. The view is `IInjectable`, so
  `UIService` runs `InjectGameObject` over the whole prefab — each page/component declares
  `[Inject]` for exactly the services/settings it needs.
- Lifecycle chains disposables: `Page.Initialize()` / `Component.Initialize()` return `this` as

- `SetContentVisible(bool)` drives the container's active state **and** the pages'
  `OnOpenDebug`/`OnCloseDebug` in code (previously the `SetActive` was wired in the Button's
  inspector onClick, so visibility and notifications could drift apart). Components `Read()` on
  every open, so shown values stay fresh.
- The namespace is `TapEmpire.UI`, deliberately not `TapEmpire.Features.Debug` — a namespace
  segment named `Debug` makes every `Debug.Log` inside it resolve to the namespace instead of
  `UnityEngine.Debug`.

**Project** — derive the popup views from the base and delete the per-project page plumbing:
`class <X>MenuDebugUIView : DebugUIView<<X>MenuDebugUIViewModel>`; former `BaseDebugPage`
subclasses become `DebugPage` subclasses (or plain `DebugPage` + components); recurring feature
blocks (settings groups etc.) become `DebugComponent` subclasses placed on the page.

## 13. Level pause

`LevelState.Pause` existed but was never assigned. It is now the pause channel, so the level state
is a small machine: `Active ⇄ Pause`, with `Won`/`Lost` reachable from either. Because `Pause` is
only entered from `Active`, leaving it is unambiguous — there is no prior state to remember. The
legal edges are not yet enforced in `SetState`, which is still a raw setter; for now the guard lives
in `ApplyPause`.

**TEL** — `ILevelExecutionCoreSystem.PauseLevel(bool)`, refcounted in `LevelExecutionCoreSystem`
next to the other level transitions. It is a counter rather than paired calls so nested popups
work, and it no-ops on any state other than `Active`/`Pause` — which is what makes the level-end
popup safe: it tries to pause, sees `Won`, does nothing, and closing it does not force `Active`.
`UICoreSystem` calls it from the same `OnBeforeOpenView`/`OnAfterCloseView` hooks as `BlockUI`,
behind the same `ShouldBlockFor` HUD filter, but on a **separate counter** so the two can diverge —
`BlockUI` is legitimately raised for in-level animated sequences that must not freeze physics.

### Ticks are now level-gated by default

`ITicksContainer.IsPaused` gates all three Zenject tick lists; `LevelExecutionCoreSystem` drives it
from a subscription to `LevelStateData.OnDataChanged`, so it follows `Won`/`Lost` set by anyone —
not only the pause counter — and resets to `false` when no level is loaded.

**This means every `ITickable` in the app stops while a level is paused**, because `ITicksContainer`
is a single ProjectContext-bound instance shared by services and core systems. Zenject's own
`TickableManager.IsPaused` is unusable for this: `TicksContainer.TryInitialize` is one-shot, so the
services container wins the race and registers everything against the *project* manager.

Anything that must keep running — timers, countdowns, heartbeats — implements the new
`IAlwaysTickable.AlwaysTick()` instead. **Audit every ticking service when migrating.** In TEL that
was `SystemService` (the one-second heartbeat every countdown subscribes to; pausing it would freeze
a shop offer's timer while its popup is open) and `PushNotificationsService`.

There is deliberately no fixed or late counterpart: `IFixedTickable` exists for physics and
`ILateTickable` for end-of-frame gameplay ordering, and neither has a legitimate always-run case.
The default is therefore the safe one — forget the marker and your service stops during popups,
which is loud, rather than gameplay running behind a popup, which is silent.

Two boundaries this does **not** cover:

- **`async`/UniTask.** UniTask runs on the PlayerLoop, not `TickableManager`, so the flag does not
  touch it. Gameplay driven by `await` needs its own guard. `Time.timeScale = 0` is the only
  mechanism that would catch both, and it is unavailable while any DOTween animation lacks
  `SetUpdate(isIndependentUpdate: true)` — it would freeze reward animations along with gameplay.
- **Physics stepping.** Gating ticks does not stop the 2D simulation; the game project freezes it
  (PopDrop flips `Physics2D.simulationMode` to `Script`, which preserves contacts and sleeping
  states, unlike sweeping `Rigidbody2D.simulated`). Both halves are required: freezing physics alone
  leaves `FixedUpdate` running, so anything applying force keeps accumulating velocity on frozen
  bodies and they slingshot on resume.

## 15. `InlineJsonConverter`

Additive. `Runtime/Utility/Json/` gained a write-only `JsonConverter` that emits its value with
`Formatting.None` while the document around it stays indented — point a `JsonProperty` at it with

## 17. `ComponentExtensions.Center`

Additive, from PopDrop's shapes.

`Runtime/Utility/Extensions/ComponentExtensions.cs` gained
`Center(this IReadOnlyCollection<Component>)` — the average of `transform.position` over the set.

`IReadOnlyCollection` rather than `IEnumerable` so the count comes for free and the average stays one

An empty set divides by zero and yields a NaN vector rather than `Vector3.zero`. Averaging nothing is

## 18. `FavoritesWindow` persistence

Behavioural, no API change.

`Editor/FavoritesWindow.cs` stored its list in `EditorPrefs` under
`TapEmpire.Favorites.<Application.dataPath>`. It now writes
`UserSettings/TapEmpire/Favorites.json` in the project, pretty-printed.

`EditorPrefs` on macOS is `CFPreferences`, which buffers through `cfprefsd` and lands in
`~/Library/Preferences/com.unity3d.UnityEditor5.x.plist` on its own schedule. A crash, a force quit
or a reboot drops everything written since the last flush, so favorites disappeared after some
editor sessions and not others. `File.WriteAllText` is on disk when it returns.

The store also destroyed itself. `Load` runs from `OnEnable`, so on every domain reload, and it fell
back to an empty `State` whenever the read came back empty or unparseable. The next drag or remove
called `Save` and persisted that empty list over the real one — a single bad read was permanent.
`Load` now records whether it succeeded in `_loaded`, and `Save` refuses to write when it did not.
The window keeps showing what it has and logs an error instead.

A missing file is a legitimate empty state, not a failed read, so a first run still saves normally.

On first load with no file present the old `EditorPrefs` value is imported and the key deleted. The
import runs once per project; nothing to do by hand.

`UserSettings/` is gitignored by the standard Unity `.gitignore`, so favorites stay per-user.

## 19. `IRaycastCoreSystem.OverlapCircle`

Additive, from PopDrop's drop box.

`OverlapCircle(Vector2 point, float radius)` returns the colliders inside a circle, filtered by the
same `_overlapLayers` mask and trigger setting as `Overlap`/`OverlapTouching`. It answers "what is
near this point" rather than "what touches this collider", so a gameplay region can be queried
without a collider existing to represent it.

It has its own buffer, `MaxCircleOverlapResults = 32`, rather than sharing the 10-slot
`_overlapResults`. A radius query is unbounded by construction — a wide circle over a dense field
overruns 10 easily, and silently truncating would turn a "nothing found" answer into a wrong one.
The same buffer caveat as `Overlap` still applies within the circle results: the segment is a view,
and the next `OverlapCircle` call overwrites it.

## 22. `SharedDisposable`

Additive, from PopDrop's merge effects.

`Runtime/Utility/Dispose/SharedDisposable.cs` gives shared ownership of a value that has to outlive
the code that finished with it — the case where a system is logically done with an object but
something else still needs it on screen. The owner constructs it with the value and the action that
disposes of it, publishes it, then calls `Dispose`; listeners call `Hold` for a lease of their own,
and the release action runs when the last lease goes. With nobody holding, the owner's `Dispose`
releases on the spot, so the un-listened path behaves exactly as a direct release would.

Same semantics as Rx.NET's `RefCountDisposable` — which R3 does not ship — plus the payload, so one
object carries both what is going away and how to keep it alive.

the level execution system and only once execution data exists.

Named `GetModule` rather than `GetExecutionModule` because the receiver already says execution.
`Module` is overloaded in TEL — `IServiceModule`, `IGenericServiceModule`, `IPurchasingModule` —
but the generic constraint scopes this one, so a module owner exposing `GetModule<T>` reads
unambiguously at the call site.

`LevelView.GetLevelModule<T>` stays as it is; the new one is the same lookup addressed through the
core system, so it is available to any execution system rather than the level one alone.

Safe to call from a module's `[Inject] Construct`: `LevelExecutionCoreSystem` assigns
`ExecutionData.Value` before it calls `InitializeModules`, so the array is populated for the whole
inject-then-initialize pass. Module order does not matter for wiring subscriptions, since module
subjects are field-initialized rather than built in `Initialize`.

## 25. Multitouch in `InputCoreSystem`

**Breaking rename**, then additive. From PopDrop, which needs more than one finger at a time.

`Screen` leaves the event names, so the single-touch members and the per-finger ones read as a pair:

| before | after | per finger |
|---|---|---|
| `OnScreenInputStart` | `OnInputStart` | `OnTouchStart` |
| `OnScreenInputEnd` | `OnInputEnd` | `OnTouchEnd` |
| `OnScreenTapEnd` | `OnInputTapEnd` | `OnTouchTapEnd` |

A pure rename — find and replace in each game. Nothing else on the old surface moved:
`InputPosition`, `IsInputStart`, `IsInputEnd`, `IsInputHold`, `BlockModeProperty`, `InputMode` and
the whole simulation path behave as before.

Added alongside: `MaxTouches`, `Fingers`, the three `OnTouch*` streams carrying `TouchInput`
(`{ Finger, Position }`), and `TouchPosition` / `IsTouchStart` / `IsTouchEnd` / `IsTouchHold`, each
taking a finger id. The `Is*` singular flags now mean "any admitted finger", which is identical
while only one is admitted.

**`MaxTouches` defaults to 1, so every existing game keeps today's behaviour with no asset change.**
A second finger is never admitted, and the single-touch stream is exactly the per-finger one. Raise
it in the installer to opt in.

Implementation notes worth knowing before changing it:

- All reported touches are read into a buffer, and `MaxTouches` gates *admission*, not the read. The
  index a touch arrives under is not stable between frames — only `fingerId` is — so reading just
  the admitted count could skip a finger that is already tracked and drop it mid-gesture.
- A finger is dropped when it lifts **and** when it stops being reported at all, via a per-frame
  `IsTracked` sweep. Without the second case a touch the platform loses holds its slot forever,
  which at `MaxTouches` 1 kills input for the session.
- A finger the UI owns still consumes a slot. It publishes nothing and all its flags stay false, but
  it is a real finger and the bookkeeping stays honest.
- The single-touch streams carry the primary finger — the oldest still admitted — so they never
  disagree with the per-finger ones; they are a filter over the same publish.

## 26. Raycasting from a given point

Additive, plus one behaviour change. From PopDrop's multitouch (section 25).

`IRaycastCoreSystem` gains `WorldPoint(screenPosition)`, `Raycast(worldPoint)` and
`Raycast(worldPoint, layerMask)`. They take the point instead of reading it, so there is nothing to
cache and no tie to whichever touch the ambient members describe — which is what makes them usable
per finger. `InputWorldPoint`, `RaycastHit2D` and `RaycastHit2DLayered` are unchanged, still cached
per frame, and still the right thing for single-touch callers.

**Behaviour change:** `DoRaycast` lost its `_camera == null` guard, so `RaycastHit2D` and
`RaycastHit2DLayered` now throw when read with no camera bound instead of returning an empty hit.
`InputWorldPoint` always threw in that case, so the three now agree. A game that reads `RaycastHit2D`
outside a level — before `ExecutionData` is set, or after it clears — will surface that as an
exception rather than a silent miss.

`WorldPoint` deliberately does not guard either: `default(RaycastHit2D)` reads as "nothing hit" and
every caller tests it, but `default(Vector2)` is the world origin, a plausible wrong answer that
would flow on into grid lookups.

## 27. `CountByExt`

Additive, from PopDrop's boosters.

`EnumerableExtensions.CountByExt(keySelector)` returns a `Dictionary<TKey, int>` of how many items
fall under each key — the `GroupBy(key).ToDictionary(g => g.Key, g => g.Count())` shape without
materialising the groups, for the common case where only the counts are wanted.

The `Ext` suffix is deliberate. .NET 9 ships `Enumerable.CountBy` with the same shape but a different
return type (`IEnumerable<KeyValuePair<TKey, int>>`), and the project is on .NET Standard 2.1 today.
Naming it apart means the runtime's version can arrive without an ambiguous-call break, and the
suffix marks every call site to revisit when it does.

## 28. Resources stop at zero

`ResourceRuntimeData.Subtract` clamps to zero instead of writing whatever the arithmetic gives, so a
spend that is not covered empties the resource rather than driving it negative and persisting that.

Callers that already gate on `HasAmount` are unaffected. Anything that leaned on a negative balance —
as a debt, or to detect an unguarded spend — no longer sees one. If a resource genuinely needs to go
below zero, that arrives as an explicit opt-in (a flag on the settings, or a `SubtractUnsafe`),
rather than by removing the clamp.

`Add` is deliberately left unclamped: going above `MaxAmount` is allowed, and only stops the
replenish timer.

## 29. `UICoreSystem.OnUpdateExecutionData` is overridable

Additive, from PopDrop's revive flow.

The handler behind the base's `ExecutionData` subscription changes from `private` to
`protected virtual`, so a game can hang per-level UI state off the same callback instead of
subscribing to `ExecutionData` a second time. An override must call base, or the block the base
takes while execution data is null is lost.

PopDrop uses it to hold a `BlockUI()` for as long as the level state is not `Active`, which covers
the window between a loss and its popup, the popup itself, and any pause a booster takes to play an
animation. That rule makes a pause imply a UI block, while `BlockUI()` on its own still blocks
without pausing — the field-movement case.

## 30. `SharedDisposable.Released`

Additive, from PopDrop's booster animations.

`SharedDisposable<T>` gains `UniTask Released`, completing when the last hold is released — the same
moment the release callback runs. The callback belongs to whoever constructed the disposable, so
until now a system that merely wanted to know when every holder had finished had no way to ask.

It is how an orchestrator waits on animations it does not own: a booster pauses the level, mutates
the model, and awaits `Released` while whichever systems chose to animate hold the disposable. A
removal nobody holds completes immediately, so the await costs nothing when there is no animation.

## 31. `IUIService.SetCanvasCamera`

Additive, from PopDrop's booster animations.

The service's canvas is `DontDestroyOnLoad` and screen space - overlay, so nothing gameplay renders
can ever draw over it. `SetCanvasCamera` switches it to screen space - camera and binds the given
camera; passing null restores overlay. Both have to move together, since assigning a camera to an
overlay canvas does nothing.

A scene that never calls it is unaffected — overlay stays the default. PopDrop binds the level
camera for the duration of a level, so a gameplay sprite can sort above the HUD by sorting order,
and clears it when execution data goes null.

Two things to check when a scene opts in: the canvas's plane distance has to fall inside that
camera's near/far or the UI stops rendering entirely, and anything that treated a `RectTransform`
world position as screen pixels is now wrong — that only holds for overlay. Convert through
`RectTransformUtility.ScreenPointToLocalPointInRectangle` instead.

## 32. `EnumerableExtensions.Shuffled`

Additive, from PopDrop's booster animations.

`List<T>.Shuffle()` shuffles in place, which a caller holding an `IEnumerable` or an
`IReadOnlyList` cannot use, and which is the wrong thing when the source belongs to someone else.
`Shuffled()` copies into a new list and shuffles that, over the same Fisher-Yates.

The names are deliberately different rather than an overload pair: with both called `Shuffle`,
overload resolution would pick in-place for a `List<T>` and copying for anything else, so the same
call would mutate or not depending on the static type of the variable.

## 33. Scoped `PauseLevel()`

Additive, from PopDrop's booster animations.

`PauseLevel(bool)` is a counter, so every caller has to pair its own release, and an early return or
a throw between the two leaves the level paused for good. The parameterless overload takes the
pause and hands back an `IDisposable` that releases it, so a booster that pauses, animates and
applies can write `using var pause = _levelExecutionCoreSystem.PauseLevel();` and stop tracking it.

Same shape as `IUICoreSystem.BlockUI()`. The `bool` overload stays for callers whose pause spans
something other than a scope, such as the UI core system taking one when a view opens and releasing
it when that view closes.

## 34. `ShibariExtensions.GetWorldPoint`

Additive, from PopDrop's booster animations.

Flying a gameplay object to a HUD element means resolving the Shibari anchor, taking its screen
point through the UI camera, and converting that back into the world — three lines that were about
to be copied per booster. `uiService.GetWorldPoint(name, camera)` is the whole operation.

The depth defaults to the camera's own distance to the zero plane, which is where a 2D game keeps
what it renders; the overload taking an explicit depth covers anything else. A name that is not in
the context throws rather than returning a fallback, since a silent default would read on screen as
a wrong animation rather than a missing binding.

## 35. A loading screen already open pauses as well as blocks

Fix, from PopDrop's boosters.

A view can open under one scene context and close under the next: the loading screen is opened
before a scene loads and closed after the next context is installed, so `UIService_OnBeforeOpenView`
raises one system's counters and `OnAfterCloseView` lowers a different one's. `OnInitializeAsync`
already compensated for that by taking `BlockUI(true)` when a `SceneLoadingUIViewModel` is already
open — it just never took the matching pause.

So Core began life at `_pauseCounter == -1`, and its first real `PauseLevel(true)` only brought it
back to zero. Nothing paused, and every later pause was silently one short, while blocking looked
fine because its half of the compensation was there.

Symptom to recognise: entering a scene through the loading screen leaves pausing dead for the
session, while entering that scene directly works.

## 36. A level starts paused

`StartLevel` holds a pause for the length of its own setup. The level view is instantiated, the save
loaded and the modules initialised while the level is `Pause`, and it becomes `Active` only once the
messages, progress and banner are done — previously it ran from the moment the level view existed,
with the rest of the setup racing it.

The pause is taken before `ExecutionData` exists, where `ApplyPause` early-returns on the null state,
so it is only the counter going up; the `ApplyPause` already inside `InitializeLevelView` is what
turns it into a state once the data is there.

Two things follow. A level start now emits `Pause` and then `Active` on `OnDataChanged`, where it
used to emit nothing, so anything keyed on state transitions sees a pair it did not before. And
`ExecutionData` is assigned before that first `ApplyPause`, so a subscriber reading the state at the
instant it receives the level still sees `Active` for that instant — correct a frame later, but not
worth relying on.

## 37. `FrameAnimation`

Additive, from PopDrop's boosters.

A sprite flipbook on an `Image`, driven by DOTween: a frame array, a frame rate, and the index of
the frame the action lands on. `Play()` returns a `UniTask` for completion and `OnImpact` fires at
that frame.

It replaces an `Animator` for the case where the whole animation is one clip whose only job is to
tell the caller when the hit connects. That normally costs a controller asset, an `Animator`, and a
component whose sole purpose is turning string-bound animation events into C# ones — where here the
caller awaits `Play()` and subscribes to `OnImpact`, both refactor-safe.

An `Animator` is still the answer when an artist needs to retime in the Animation window, or when
there is a real state machine to blend.

- Ads on quit/restart follow the new booleans.
- Frame rate comes only from `SystemSettings.FrameRate`.
- `IsInputHold` stays true on device while a finger rests without moving.
- Taps on HUD and debug buttons no longer reach gameplay, and a press begun on a button then dragged
  onto the field stays swallowed for the whole gesture (section 7).

- Simulated gestures chain from where the previous one ended (autoplay / creatives finger).
- Raycast blocking: in WordGame, confirm the coin timer still swallows taps — it will not unless a
  blocking tag was configured to replace `IInterceptRaycaster` (section 8).
